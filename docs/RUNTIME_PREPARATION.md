# Preparing semantic programs in the runtime

The experimental runtime entry point accepts the same public `Program` as
`ynn-compile`. It lowers, verifies assets, constructs both phase graphs, and
prepares them once in the calling process. Invocation reuses those graphs.
Offline `.ynn` packages remain the default and remain useful for inspection,
reproduction, and environments that do not need model authoring.

```text
source importer ─┐
                ├─> Program + immutable assets ─> runtime::prepare
Rust author ────┘                                      │
                                     PreparedProgram + ExecutionSpec
                                                      │
                                                  Session
```

## API and command line

`ExecutionSpec` describes phase inputs, token/position/mask recipes, logits,
embeddings, persistent resources, and fixed state. It has no plan filenames or
plan hashes. An offline package adds those artifact identities around the same
execution metadata. Asset byte counts and hashes remain mandatory in both paths.

With the `llm` feature, a library caller can prepare and invoke a model as follows:

```rust
use std::path::Path;
use ynnpack_lab::runtime::{self, AssetStore, PrepareOptions, Session};

// `program` comes from a Rust author or a deserialized public Program.
// `execution` describes this program's phase interface and state.
let assets = AssetStore::open(Path::new("bundle"), Path::new("parameters"))?;
let prepared = runtime::prepare(&program, assets, PrepareOptions {
    threads: 4,
    execution: Some(&execution),
    ..Default::default()
})?;
let mut session = Session::from_prepared(prepared, execution)?;
drop(program);
session.invoke(&[42], true, None)?;
let logits = session.logits();
```

Library callers must provide the same 64 MiB preparation-thread stack used by
the runners for large Slinky graphs. Build and link through the CMake integration;
the native backend and Rust operation archive are required.

Prepare public Qwen3 assets as described in [COMPILER.md](COMPILER.md), then run
the Rust author directly without first creating `.ynn` files:

```sh
build/ynn-llm --qwen-assets=out/qwen-assets/assets.json \
  --bundle_dir=out/qwen-assets --parameter_dir=out/qwen-assets/parameters \
  --cache_capacity=2048 --prefill_rows=128 --num_threads=4 \
  --cases_file=models/qwen3_0_6b/fixtures/matrix.tsv \
  --output_dir=out/qwen-runtime --warmup_runs=1 --measured_runs=3
```

For a serialized semantic input, substitute `--program=program.json` and
`--execution=execution.json`. The latter defaults to a sibling `execution.json`.
These inputs are mutually exclusive with `--graph_dir` and with each other.
The original `--graph_dir` interface continues to load offline packages.

## Ownership and preparation boundary

There is one semantic compiler and one set of lowering rules. The prototype
reuses in-memory `.ynn` emission and parsing, so it requires no compiler
subprocess or temporary plan files. It does not yet have a direct typed native
builder or persistent preparation cache. Compilation reports, text, and temporary
generated-constant vectors are released after preparation.

Source weights use immutable mappings. Generated constants use owned, aligned
storage with backend padding. Prepared graphs retain the asset owner and are
dropped before that storage. All phase interfaces and referenced assets are
validated before native graph construction. A failure in a later phase drops
earlier prepared graphs; callers receive a prepared object only after all phases
succeed. `Session::from_prepared` checks that its execution specification matches
the one validated during preparation.

Sessions require exclusive mutable access and are neither `Send` nor `Sync`.
Logit borrows prevent concurrent mutation. Position stays a dynamic scalar;
attention sees the live KV prefix, and append updates only the new rows.
Resource-update outputs share their owner's binding. No extra buffer or history
copy is introduced for those aliases. A late execution failure poisons the
session; existing reset/discard rules still apply.

`setup.json` separates model loading/authoring, semantic compiler stages, text
parsing, interface checks, asset verification, native construction, and native
compilation. It also records generated bytes, text bytes, compiler call count,
RSS, and allocator observations where available. `--prepare-drop=4` runs a
diagnostic lifecycle experiment with observations before preparation and after
drop. It retains the source program across iterations and produces no valid
inference latency measurement.

## Rust operation and native kernel boundary

`rust/operations` owns the complete group-32 asymmetric-A8/symmetric-W4 fully
connected operation: activation quantization, INT4 unpacking, K1/K4 packing,
zero-point correction, group accumulation, scratch, and task partitioning.
The C++ bridge exposes backend capabilities, opaque kernel handles, kernel
invocation/state, and synchronous access to Slinky's existing thread pool.

ISLE rules select a compatible strategy in this order:

1. Unsigned-A/signed-B K4 dot.
2. Signed-A/signed-B K4 dot, shifting both activation codes and zero points by 128.
3. Portable unsigned-A/signed-B K1 dot.

The signed strategy requests the backend's symmetric-B variant. Selection checks
the returned kernel's packing and tile constraints. Requested feature masks can
only disable detected CPU features. AMX is excluded because its minimum row tile
does not fit this operation's unpadded row buffers. Synthetic capability tests do
not execute unsupported instructions.

Descriptors for row buckets 1 through 8 are queried during preparation. Invoking
an operation selects a prepared bucket and allocates no new kernel descriptors.
Activation scratch grows to the largest invoked row count and is reused. Each
worker uses 8,704 bytes of Rust tile scratch plus opaque native kernel state;
weights remain packed INT4 between calls. There is no full decoded-weight cache
and no independently maintained C++ implementation of the operation.

## Validation and measurement

CTest covers offline/runtime fixture equivalence, independent blockwise
arithmetic, native and restricted-feature dispatch, output/resource interfaces,
mapping and generated-constant lifetimes, later-phase failure cleanup, repeated
prepare/drop, session transitions, and compile-time ownership restrictions.
`tools/test_compiler_fixtures.py --runtime` executes semantic inputs while still
checking the frozen offline compiler artifacts. See the tool's help for paths.

The Qwen3 recipe currently uses INT8 linears. A Qwen comparison alone therefore
cannot validate or measure the W4 operation. Generate a separate, reproducible
shape matrix with an archived baseline compiler:

```sh
python tools/prepare_runtime_bench.py --compiler "$BASELINE/ynn-compile" \
  --output out/blockwise-runtime
"$BASELINE/plan_fixture" out/blockwise-runtime/offline-t4.json
build/plan_fixture out/blockwise-runtime/runtime-t4.json
```

The generator includes channel tails, reduction groups, and rows 1/17/128.
Use its `*-check.json` inputs for output comparisons, separately from timing.
Compare frozen offline, in-process/native-operation, and in-process/Rust-operation
binaries in alternating fresh-process pairs with identical assets and affinity.
Keep setup, warm TTFT, decode, memory, and binary size separate. A lower startup
cost does not explain a warm execution improvement, and a higher startup cost
alone does not reject the runtime boundary. See [BENCHMARKING.md](BENCHMARKING.md)
for timing definitions and device controls.

This interface remains experimental. Broader model/device coverage and the
paired correctness, memory, and latency decision gates must precede a default
change. Missing evidence or a confidence interval crossing a gate is inconclusive.
The [October 22 prototype report](../results/runtime_preparation_20261022/README.md)
records the measured outcomes and the remaining qualification limits.
